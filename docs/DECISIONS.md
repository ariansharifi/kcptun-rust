# Decisions & Deviations Log

- **D-xx:** architecture and implementation decisions. These are internal and never visible on the wire.
- **V-xx:** intentional *behaviour* deviations from the Go reference. Each one must be wire-compatible
  and clearly better, and must have evidence.

**Status values:**
- **Accepted:** proceed.
- **Proposed:** default chosen, but the user should confirm. Work may continue on the default.
- **Needs user:** blocking; ask before the step that depends on it.
- **Superseded:** replaced by a later entry.

When a decision changes: add a new entry, mark the old one Superseded, and reference both in the commit.

## Architecture decisions

| ID | Status | Decision | Rationale |
|---|---|---|---|
| D01 | Accepted | **tokio** multi-thread runtime (worker threads = CPU count). Honour `GOMAXPROCS` if set, as a nicety for existing deployments. | Mature, efficient timers and I/O, maps cleanly from goroutines. |
| D02 | Accepted | KCP session = `Arc<Inner>` with `Mutex<SessionState>` (KCP + FEC decoder + recv buffer) plus `tokio::sync::Notify` for read and write events. No syscalls, crypto or allocations-in-a-loop inside the lock. | Mirrors Go `mu` + `chReadEvent`/`chWriteEvent`, keeps identical semantics, minimal hops on the input path. |
| D03 | Accepted | Replace `SystemTimedSched` with a per-session update task: `sleep_until(now + flush())`. | Same scheduling semantics. tokio's timer wheel is O(1) and there is no global heap to contend on. |
| D04 | Accepted | Output pipeline = per-session bounded channel (cap **2048**, `try_send`, drop when full) → tx task: FEC → encrypt → batch until the channel is empty or 64 msgs → rate limiter → send. | Same as Go `postProcess` (keeps crypto and syscalls out of the lock). |
| D05 | Accepted | Own thin `recvmmsg`/`sendmmsg` wrapper (libc) on Linux, per-packet I/O elsewhere. Unconnected UDP sockets like Go. **No** DF/PMTU socket options. `quinn-udp` rejected because it sets DF. GSO/GRO only as a measured opt-in (Step 12). | Behavioural fidelity (fragmentation behaviour unchanged) plus Go's batching. |
| D06 | Accepted | Packet buffers are fixed 1500-byte (`mtuLimit`) buffers from a bounded lock-free pool with an RAII handle that returns on drop. | Go uses `sync.Pool`. RAII makes leaks and double-puts impossible. |
| D07 | **SETTLED (11.4b, 2026-09-24, controlled same-box test). mimalloc REJECTED. glibc is the DEFAULT for released Linux artifacts and for the container image; static musl is a documented fallback with a loud warning.** | This entry flipped twice before; the run that settles it holds everything constant on ONE box (lab-arm64, aarch64, 2 vCPU, same kernel, netem, S1 flags, churn seed, and the workload driver deliberately not redeployed) and changes only the allocator: **musl peaks at 253 MiB and releases 0% after traffic stops, ramping +44,860 kB/h; glibc peaks at 50 MiB, falls to 13.6 MiB within two minutes (73% released) and has a *negative* slope of −600 kB/h.** 5x in peak, 75x in slope. The throughput confound I feared does not exist — the churn is rate-driven, so all runs delivered 36.7–36.8 Mbit/s at the same latency (p50 103.02 ms both) and the same CPU (8.5% both). **Why the earlier musl call was wrong:** 13.2c measured a *single burst at small scale* in Docker Desktop's VM, with peaks under 20 MB — a regime where musl has nothing to ratchet, so it looked cheaper. The user's mesh is the other regime: long-running, continuously churning. **The warning musl needs is stronger than 'keeps its high-water mark':** under sustained churn it **ramps 32–45 MiB/h and had not flattened after six hours** (79 -> 253 MiB). On a 961 MB box that is an OOM within a day. Remaining confounds, stated: n=1 per arm with no interleaving (step 12 rule 1 unmet, though the effect is orders of magnitude outside any plausible spread); different durations (restricting musl to glibc's two hours still leaves it at 135 MiB, 2.7x, still climbing); different time of day; and the gnu binary is a PIE against the system libc where the musl one is static. **Also learnt:** `memory::trim_when_idle` **never fired once** in either six-hour run — the churn keeps the process busy every tick — so the glibc plateau is held by ordinary `free()` alone, and the all-or-nothing quiet rule costs a busy glibc process nothing. It only acted in the 100 s after traffic stopped (45.3 -> 13.6 MiB). |

| D29 | Accepted (implemented and measured in 12.2c, 2026-09-23) | **`flush()` skips the part of `snd_buf` it has already scanned.** Go rescans the whole send buffer on every flush — every write, every update tick and every ACK that advances `una` — which at the production window (`-sndwnd 8192`) walks 8192 x 64 B of `Segment` per call. `Kcp::flush_scan` keeps three deliberately **conservative** facts about the segments the last scan covered: a *lower bound* on the earliest `resendts` of a transmitted unacknowledged segment, a flag cleared by `parse_fastack` whenever a fast retransmit may be pending, and the length of the never-transmitted contiguous suffix. Each may claim **less** than is true — costing a full scan and nothing else — and can never claim more; a scan that finds the invariant broken sets `ScanBound::Unknown` and gives the optimisation up. When the bound is at least one `interval` ahead and no fastack is pending, the loop starts at `snd_buf.iter_mut_from(skipped)`. | **Recorded as D-xx, not V-xx, deliberately**: docs/porting-guide.md §2 rule 4 reserves V-entries for *observable* differences, and this one has none by construction — byte-identical packets, identical state, identical `nextUpdate`. It is an internal algorithmic choice, architectural enough to record because it introduces an invariant that any future change to `snd_buf` must maintain. Measured on the M5, medians of 5 interleaved runs: **flush/1024 1.127 us -> 25.5 ns (44x), flush/8192 8.790 us -> 25.3 ns (347x)** — O(1) in the window rather than O(window). Proven inert against the D25 oracle on 12 randomised lossy/reordering traces plus 8 V18-backpressured ones (identical bytes per endpoint, identical state words, identical retransmission counts, identical `nextUpdate` from every flush), Go golden traces and sim summaries unchanged, and a 100 s `kcp_input` fuzz run (435,860 execs) clean. **Accepted cost:** the scan that *cannot* be skipped is **26-30% slower on the M5, but only 9-10% slower on the Neoverse-N1** (12.2e: +10.1% at 1024, +9.3% at 8192), because the summary costs three register operations per segment — the same 0.32 ns/segment on both machines, against an N1 loop that was already 3.49 ns/segment to the M5's 1.07. A transfer in a sustained loss storm, where nearly every flush has a segment due or a duplicate ACK pending, pays that on every flush. The trade is 347x-408x in the common case against 1.1x-1.3x in the pathological one, and the lossy and jittery profiles of 11.2/11.3 are where it must be confirmed on a real path — the 46.3 ms lab-x86-2/lab-x86-3 pairing (mdev 6.6 ms) is the natural test. **Also note:** the D25 oracle is now the same code path with `flush_scan.enabled = false`, not a separate naive copy — better, in that the two cannot drift, but the oracle still carries this bookkeeping and is no longer byte-for-byte the pre-12.2c function; the Go golden traces still validate the loop body against kcp-go itself. **N1 numbers taken in 12.2e** (aarch64, medians of 5 interleaved rounds, docs/benchmarks/kcp.md section 12.2e): **flush/1024 3.569 us -> 70.2 ns (50.8x), flush/8192 28.576 us -> 70.1 ns (408x, and 902x Go)** — the predicted larger ratio held. It also found an effect this entry did not claim: `Kcp::input` flushes on every slide of the send window, so D29 makes the *ordinary in-order* ACK path **6.65x** faster at the production window (2.381 ms -> 358.1 us, 15.8x Go). D29 is therefore a large win on the commonest path, not only on the rare full flush. |

Unknown errnos keep Go's own numeric fallback. | **This is the faithful choice, not a workaround.** Go does not call `strerror` either — it has its own generated table (`syscall/zerrors_linux_amd64.go`: `98: "address already in use"`). Taking the C library's string only ever *looked* right because glibc happens to agree with Go for common errnos. 10.5 found where it does not: a **static musl** build prints `bind: address in use` where Go and glibc print `bind: address already in use`, failing `addr::tests::a_failed_tcp_bind_reads_like_gos_net_op_error` and a `kcptun-server` test on that target only. | D31 | Accepted (implemented and measured in 12.2d, 2026-09-23) | **The ACK path addresses a segment by its sequence number instead of searching for it.** `snd_buf` holds `snd_una ..< snd_nxt` ascending with no gaps — `flush` only ever appends `sn = snd_nxt`, `parse_una` only discards a prefix from the head, an ACK only sets `acked` and frees the payload (kcp-go's own reason for leaving acked segments in place), and `shrink_buf`, which Go's `Input` runs before every `parse_ack`/`parse_fastack`, sets `snd_una` to the head's `sn`. So the segment an ACK names sits at ring offset `sn - snd_una` (wrapping subtraction, so anything below `snd_una` wraps past any ring length and the single bounds check covers it). `Kcp::snd_buf_offset` **verifies** that the segment at that offset actually carries `sn` and returns `None` otherwise, and the caller then falls back to kcp-go's linear scan — correct whatever the ring holds. `parse_ack` becomes O(1) in the window; `parse_fastack` uses the offset only as its loop bound, since its per-segment `fastack` write *is* the algorithm. | **D-xx, not V-xx**, for the same reason as D29: no observable difference — identical packets, identical per-segment state, identical `nextUpdate`. It shares D29's `FlushScan::enabled` master switch and its summary of `snd_buf`, deliberately, so the two cannot disagree about the ring. M5, medians of interleaved rounds: **input_ack/sack/8192 43.48 ms -> 24.97 ms (1.74x, and 4.8x Go); sack/1024 639 us -> 386 us (1.65x, 4.7x Go)**. `in_order` is unchanged **by D31** by construction — a cumulative `una` retires those segments before `parse_ack` sees them (D29 does change it: see 12.2e). The flush loop has no source change, so this adds nothing to D29's accepted 26-30% full-scan cost. Proven inert against the D25 oracle on 12 randomised loss/reorder/duplicate-ACK traces (identical wire bytes, per-segment digest, retransmission counts and every `nextUpdate`), Go golden traces unchanged, 121 s `kcp_input` fuzz (380,755 execs) clean. **Every debug-assertions build cross-checks the computed offset against the full scan on every ACK** — tests, golden traces and fuzzing all run that net — so the offset is trustworthy, but the ACK path must never be benchmarked from a debug build. **N1 numbers taken in 12.2e** (aarch64, release, medians of 5 interleaved rounds): **input_ack/sack/8192 143.03 ms -> 85.61 ms (1.67x, and 4.1x Go); sack/1024 2.309 ms -> 1.454 ms (1.59x, 3.7x Go)**. docs/benchmarks/kcp.md predicted the N1 would gain *more* than the M5's 1.74x/1.65x; it gains marginally **less**, and only the wall-clock saving is larger (57.4 ms per window against 18.5 ms). The prediction is corrected in that document: D31's speed-up is a property of the algorithm and is near-identical on both microarchitectures. |
| D32 | Accepted (2026-09-24) | **11.2's acceptance is evidenced on a partial grid, and the reason the full grid would not have been better is the host, not the time.** 16 of the 28 bulk cells were run: S1 over all seven netem profiles, S2 over clean/wan50/lossy10, S3 and S4 over the discriminating `lossy10`, plus a capped control and three S1 latency cells. | D33 | **OPEN — under investigation, deliberately NOT accepted (12.1b, 2026-09-25)** | **Median latency under a competing bulk flow is far worse than Go's, while every other percentile is better.** S1 latency-loaded on lab-x86-1: **p50 0.52 ms (Go) against 15.04 ms (Rust), 29.20x**, five-run sets 13.01-15.96 against 0.43-0.91 with no overlap.

# 11.3b: the 95.3 ms rung, re-taken with provenance

Session of **2026-09-24, 22:09–23:48 UTC**, driven from the laptop by `tools/lab/lab.py` in its
two-host `wan` mode: **`lab-x86-2` runs the client, `lab-arm64` runs the server**, no netem
anywhere, both ends sampled and collected separately.

> **Read this first.** This is a real Internet path between two of the lab VPSs. Its capacity,
> its queueing and its cross traffic belong to somebody else, so **a number here may only be
> compared with another number from the same session.** The pairs ran interleaved (GG, RR, GR,
> RG, repeated) precisely so that whatever the path was doing happened to Go and to Rust alike.
> The next session on these two hosts will give different absolute numbers and: this is the
> claim: the same relative ones. Both hosts' `uptime` is recorded before and after **every** run,
> in the detail documents.

## Why this session exists

[11.3](11.3-wan-matrix.md) measured one rung (lab-x86-3 → lab-arm64, 131.1 ms) in 27 runs whose
**`server_build` is the empty string in every one**, because the `kr-server` on lab-arm64 had no
`BUILD.txt` beside it. Its headline is **the only place in the whole project where Rust appears
to lose on throughput**: 0.75× Go on the S1 upload. An unflattering result that nobody can check
is the worst kind to leave standing, so it was re-taken properly.

It could not be re-taken *as itself*. 12.0 made a run **refuse to start** on a host whose build
stamp cannot be read, and the binary that produced those numbers is gone; a repeat of that exact
session is impossible, and 12.0's refusal does not retrospectively validate it. What this session
does instead is take **the same shape of rung**: a 1-vCPU x86_64 client sending over a
long, clean, transatlantic path into a 2-vCPU aarch64 server, the same S1 and S2 profiles, the
same scenarios, the same interleaving, with **every artefact on both ends stamped, hashed on the
host and recorded in the run**.

Three things differ from 11.3 besides the provenance, and all three are stated here rather than
buried:

1. **The rung is 95.3 ms, not 131.1 ms**, and the client is lab-x86-2, not lab-x86-3. A different
   rung cannot prove a number taken on another one wrong. What it can do is say whether the
   effect survives on a provenanced rung of the same shape. (It does not, see
   [the retraction](#what-this-does-and-does-not-say-about-the-075-headline).)
2. **The socket-buffer ceiling is recorded.** D32: `setsockopt(SO_RCVBUF)` is silently clamped to
   `net.core.rmem_max`, and a stock Ubuntu ceiling of 208 KiB against S1's `-sockbuf 8388608` was
   the entire explanation for three failing cells of the 11.2 matrix. lab-x86-2 was raised to
   8388608 / 67108864 on 2026-09-24 (`/etc/sysctl.d/99-kcptun-lab.conf`) and lab-arm64 has had
   those values all along; both are recorded in every `state.json` of this session and printed
   in the header of each of the three detail documents, with the preflight warning about the
   server's `-sockbuf 67108868` against `rmem_max` printed in each run's log. The 11.3 session **recorded neither host's ceiling**: `socket_buffer_limits`
   did not exist in `lab.py` at its revision (`03afc40`), so whether its client was clamped is
   not knowable from its record. (lab-x86-3 reads 8388608 / 8388608 *today*, with no config file
   naming either value; that is evidence, not provenance.)
3. **The iperf3 guard rail had to move.** See below: 400M binds on this rung.

### The guard rail, and why it moved

`iperf3 -b` is a cap against saturating a host's NIC (tools/lab/README.md rule 6), not part of the
measurement, and **a cap that binds makes every implementation report the cap**. The committed
scenarios carry `400M`, chosen for the 131 ms rung where nothing reached it. On this rung a
throwaway Go↔Go probe before the campaign (`wan-s1-probe`, 20 s each way at `900M`) drove
**631 Mbit/s up**, so 400M would have bound, and bound on the very cell this session exists to
re-take. That probe's record lives only in `lab-runs/`, which is gitignored, and **no goodput
from it is used as a result**; but its 631 Mbit/s is what `--bitrate` is set against, and it is
quoted as exactly that justification in `tools/lab/README.md`, in the `--bitrate` help text and
`cmd_run` comment of `tools/lab/lab.py`, and in both `wan-*` scenario descriptions.

The cap is therefore a property of the path, not of the scenario file, and `lab.py run` gained a
`--bitrate` override for it. This session ran at **`-b 900M`**, applied to every iperf3 workload
of every pair in both directions, and the highest single run reached 683 Mbit/s, so it never
bound. `lab.py` now also prints each workload's full command line into the report, so the cap is
visible on the page a number is quoted from rather than only inside `state.json`.

### The retransmission counters, as rates

kcp-go accumulates `RetransSegs = LostSegs + FastRetransSegs + EarlyRetransSegs`
(`reference/kcptun/vendor/github.com/xtaci/kcp-go/v5/kcp.go`, the "counter updates" block of
`flush`) and Rust matches it, so all three components are quoted and the total is fully
attributed with no remainder. Each cell is the **median over that pair's repetitions of each
run's own ratio**, which is why components do not add to the total to the last digit; within any
one run's totals (in the detail document) they add exactly.

| | GG | RR | GR | RG |
|---|---:|---:|---:|---:|
| client segments sent (`OutSegs`) | 4.51 M | 5.35 M | 5.70 M | 5.64 M |
| client **retransmitted** (`RetransSegs`), % of sent | **0.23** | **1.58** | 0.94 | 1.63 |
| …of which RTO-driven (`LostSegs`), % | 0.23 | 1.57 | 0.94 | 1.63 |
| …of which fast (`FastRetransSegs`), % | 0.000 | 0.005 | 0.000 | 0.003 |
| …of which early (`EarlyRetransSegs`), % | 0.000 | 0.000 | 0.000 | 0.000 |
| server **duplicates received** (`RepeatSegs`), % of received | **0.23** | **1.58** | 0.94 | 1.64 |
| server segments sent (`OutSegs`) | 1.97 M | 2.89 M | 2.34 M | 2.41 M |
| server **retransmitted** (`RetransSegs`), % of sent | **38.0** | **10.8** | 13.8 | 31.1 |
| …of which RTO-driven (`LostSegs`), % | 26.8 | 7.3 | 9.3 | 22.1 |
| …of which fast (`FastRetransSegs`), % | 10.8 | 3.5 | 4.5 | 8.8 |
| …of which early (`EarlyRetransSegs`), % | 0.28 | 0.07 | 0.10 | 0.20 |
| client duplicates received, % of received | 23.2 | 7.1 | 8.8 | 18.0 |
| `FECRecovered` / `FECErrs` / `InErrs` / `KCPInErrors` | 0 | 0 | 0 | 0 (S1 has no FEC) |

Three things to take from it.

**The spurious-retransmission finding of 11.3 holds exactly.** On every pair the receiver's
duplicate rate tracks the sender's retransmit rate to the second decimal (0.23 → 0.23,
1.58 → 1.58, 0.94 → 0.94, 1.63 → 1.64): the segment that was retransmitted had already arrived.
Both implementations do it, and it is what the `RetransSegs` totals on this path mostly are.

**Rust's client-side share is the larger one at the pair medians (6.9× Go's) but at a sixth of
the level 11.3 saw, it costs nothing here, and the per-run ranges overlap completely.** 11.3
measured 9.31 % against 3.16 %; this session measures **1.58 % against 0.23 %** at the pair
medians, with the same ~99.7 % RTO-driven composition, and the pair that retransmits more is also
the pair that moves more data.

The goodput section above abandons pair medians for pooling by sender, because three repetitions
on a path this noisy cannot carry a per-pair claim. The same treatment has to be applied here, and
it costs the finding most of its size. Per run, client `RetransSegs` as a share of client
`OutSegs`:

| | r1 | r2 | r3 |
|---|---:|---:|---:|
| **GG**: Go client | **5.79 %** | 0.005 % | 0.23 % |
| **GR**: Go client | 0.94 % | 2.28 % | 0.22 % |
| **RR**: Rust client | 1.57 % | 1.58 % | 2.28 % |
| **RG**: Rust client | 2.37 % | 1.32 % | 1.63 % |

Pooled by *which end is sending*: the median over all six runs each, exactly as the goodput table
pools: that is **0.58 % for a Go client against 1.61 % for a Rust client, 2.8×**, not 6.9×.
Weighted by segments sent rather than taken as a median it is 1.46 % against 1.77 %, 1.2×, because
the single 5.79 % Go run dominates that form. And **Go's own range (0.005–5.79 %) brackets Rust's
entire range (1.32–2.37 %)**, with Go's GG r1 higher than every Rust run of the session. So the
ordering holds at the pair medians and pooled by sender, but the two ranges overlap completely:
this session shows a **tendency, not a separation**. The magnitude of 11.3's gap is not
reproduced, and neither is its consequence.

**In the other direction the ordering reverses, and by a lot more.** Sending from lab-arm64, Go
retransmits **38.0 %** of its segments against Rust's **10.8 %** on a path that is genuinely lossy
for both, and Rust delivers 1.65× the goodput at 0.60× the CPU per gigabyte. 11.3 found the same
shape (37.9 % against 23.2 %).

**The confound 11.3 named is still here and still unsettled.** Direction and host are not
separable on this rung either: "client sends" is also "a 1-vCPU x86_64 box sends into a clean
direction", and "server sends" is also "a 2-vCPU aarch64 box sends into a lossy direction". The
rungs that would separate them are the ones between two identical 1-vCPU x86_64 boxes (5.1 ms and
56.7 ms), and neither has been run.

**Pooled by sender, as the S1 goodput table pools**: the median over all six runs with that end

**This is the window limit, and both implementations sit on it.** A 128-packet send window at
95 ms is 128 × ~1.35 kB / 0.095 s ≈ 14.5 Mbit/s, and every cell is in the 9–13 Mbit/s band below
it. 11.3 made the same observation at 131 ms, where the ceiling is ~10 Mbit/s and both
implementations produced ~8.5 Mbit/s. Retransmissions are in the hundreds rather than the
hundreds of thousands, in both directions and for both implementations, **with one exception the
medians hide.** In `wan-s2-bulk-gr-r2` the **Rust server** retransmitted **6,388** segments, 6.87%
of what it sent, against a GR pair median of 0.05% and against 0–355 on every other run of the
scenario. 99.9% of it was RTO-driven (`LostSegs` 6,382, `FastRetransSegs` 6) and essentially all of
it was spurious: the Go client recorded **6,427** duplicates, so every retransmitted segment had
already arrived. It cost nothing: that run has the highest GR download of the three (12.2 Mbit/s).
It is one run in twelve and the only adverse Rust datapoint in the S2 set, so it is recorded here
rather than left under the median; three repetitions cannot say whether it is the path or the
implementation.

`FECRecovered` is 0 on **ten of the twelve** runs, and the table's zeros are medians of three, so
they hide the two that are not. Both of those are **mixed pairs, in opposite directions**: GR r1
recovered **5** segments on the Go client from the Rust server's parity, and RG r1 recovered
**11** on the Rust client from the Go server's (the `wan-s2-bulk-gr-r1` and `wan-s2-bulk-rg-r1`
SNMP blocks of [`11.3b-wan-x86-2-arm64-s2-bulk.md`](11.3b-wan-x86-2-arm64-s2-bulk.md)). **Every segment
FEC reconstructed in this session was reconstructed across implementations**, in both
directions, which is positive interop evidence for the Step 04 FEC layer rather than noise.
11.3's S2 table points the same way without being as clean: its 0.5 medians for GR and RG are
one recovered segment each on GR r1 and RG r1, and its third and last recovery of the session
was on GG r3 (three segments over nine runs, all client-side).

Sixteen recovered segments over twelve runs is still not a *test* of FEC: at 11 Mbit/s this path
loses almost nothing, so FEC 10/3's 30 % of parity bought nothing. That is not evidence against
FEC: it says this rung, at this rate, is not where FEC gets tested. The 46.3 ms jittery rung
(mdev 6.6 ms) still is, and it is still unrun. S1 carries no FEC, and its 12 bulk runs and 2
latency runs are `FECRecovered` 0 throughout.

These are single-run totals rather than medians of ratios, so each `RetransSegs` is exactly the sum
of the three components beneath it (Go client 3 780 044 + 1 182 774 + 13 348 = 4 976 166, and so on
for the other three).

**This is the V18 (tx-channel backpressure) result, and it is the same one 11.3 reported, now on
provenanced binaries at both ends.** With a bulk flow and an interactive stream sharing one
tunnel over a real 95 ms path, Rust is faster at *every* percentile, including the tail, where it
removes 43 % of the worst case, **and** carries 43 % more bulk while doing it, on 45 % of the CPU
per gigabyte.

The sender-side retransmission picture inverts completely here, which is the part worth holding
on to. A
**single** upload stream is where Rust's retransmit share is the larger one (1.58 % against
0.23 %). Put a competing flow beside it (which is what a tunnel actually carries) and **Go's
client retransmits 21.6 % of everything it sends against Rust's 0.53 %**, a factor of 40 the
other way, while Rust delivers more. A report that quoted only one of those would be misleading,
so both are here, as they were in 11.3.

**The two counters in that table that go against Rust are receiver-side ones.** The Rust client
*receives* **21.2 %** duplicates against Go's 14.1 %, even though the Rust server retransmits less
than Go both absolutely (3.09 M against 4.74 M) and as a share of what it sends (24.2 % against
31.9 %). The explanation is spuriousness, and it is what the two sides of each pair say together:

| direction | retransmissions sent | duplicates arriving | spurious |
|---|---:|---:|---:|
| GG, server → client | 4 743 432 | 1 667 470 | 35 % |
| RR, server → client | 3 091 709 | 2 602 002 | **84 %** |
| GG, client → server | 4 976 166 | 2 876 364 | 58 % |
| RR, client → server | 134 880 | 127 453 | **94 %** |

So under this workload **Rust sends far fewer retransmissions than Go in both directions, and a
much larger fraction of the ones it does send are duplicates of segments already delivered**,
84–94 % against Go's 35–58 %. Neither half of that describes the run on its own: the share of the
link Rust wastes on retransmission is the smaller one in both directions, and the share of its own
retransmissions that turned out to be needed is the smaller one too.

Two limits on this table: **one run per pair** (a ten-minute run on a shared path), and **no
mixed pair**: GR and RG are covered for interop by the 24 bulk runs, but nothing here shows a
mixed pair under the latency-under-load workload. Both are the same gaps 11.3 had.

## What this does and does not say about the 0.75× headline

**Retracted as a property of this tree.** The claim "Rust is 0.75× Go on the S1 upload over a
real WAN path" must not be quoted, in the report or anywhere else, as a measurement of this
implementation. It rests on a session in which the server artefact was never identified, and it
does not reproduce on a provenanced rung of the same shape: **1.17× on the pair medians, 1.03×
pooled by sender, with the path's own spread wider than either figure.** Every acceptance cell of
this session clears 11.2's 0.95× bar.

**Not retracted as a record of what happened that night.** A different rung cannot prove a number
taken on another rung wrong. 11.3's 131.1 ms session is still on the record, still says what it
says, and is still unprovenanced; what has changed is that there is now a provenanced measurement
of the same question, and it is the one to quote. The honest summary of the pair of sessions:

- the **S1 upload deficit** appears on exactly one rung, measured once, with an unidentified
  server binary and no record of either host's socket-buffer ceiling. It is **not confirmed**;
- the **elevated RTO-driven, almost entirely spurious client-side retransmission on a single
  upload stream** appears on both rungs, with provenance on this one. It is a **tendency, not a
  separation**: 6.9× Go's share at the pair medians, 2.8× pooled by sender, and Go's per-run
  range brackets Rust's entirely, and it is **not** costing goodput at 95 ms;
- the **server-side** result (Rust retransmits a third of what Go does while delivering 1.65×)
  and the **latency-under-load** result (better at every percentile, more bulk, 40× fewer
  retransmissions) appear on both rungs and are the larger effects.

**No DECISIONS entry is written for the middle bullet** (orchestrator decision, 2026-09-25), and
the reason is the data rather than the effort. Go's per-run range **brackets Rust's entirely**
(Go 0.005–5.79%, Rust 1.32–2.37%), the sign **reverses** when the server is the sender (Go 38.0%
against Rust 10.8%) and reverses again by roughly 40× under a mixed interactive-plus-bulk workload
(Go 21.6% against Rust 0.53%), and it costs no goodput at 95 ms. The V-table is what the README
publishes as "differences from Go", and a tendency inside overlapping ranges that inverts under two
other configurations is not a difference: writing it there would give a noise-level observation the
same standing as V11's data-loss fix. It stays recorded here, which is where a tendency belongs.
**What would settle it:** a rung between two *identical* boxes, so the asymmetry between a 1-vCPU
x86_64 client and a 2-vCPU aarch64 server stops being a candidate explanation. That is the first
thing to do if a future rung ever shows it costing throughput.

## Caveats

1. **Within-session only.** Stated at the top, repeated here because it is the one that matters.
   Nothing in this document may be compared with a number from 11.3's session, including the
   tables that look directly comparable: different rung, different client host, different night.
2. **The upload direction is noisy on this rung** (±20 % within a pair, against ±2–3 % on the
   download's Go-sending arm and about ±8 % on its Rust-sending arm). Three repetitions per pair
   are enough to say "no deficit" and not enough to quantify a small advantage.
3. **Direction and host are confounded**, exactly as in 11.3 (above).
4. **The load gate is per session, not per run.** lab-arm64's load average reached 3.0–3.15 on
   2 vCPU during rounds 2 and 3 of the S1 session, so later rounds ran on a busier server than
   the first, for every pair equally, which is what the interleaving is for, but it is why the
   per-pair spreads are what they are. Every run's `uptime` on both ends is in the detail
   documents.
5. **The bitrate cap.** `-b 900M`, above the 683 Mbit/s the fastest run reached, so it never
   bound. If a future rung on these hosts reports a flat 900.0, the cap has become the
   measurement and the run is void. The full iperf3 command line of every workload is now printed
   in the report, so this is checkable from the page.
6. **lab-arm64 is not a quiet box.** It carries a live kcptun deployment of its own (27 clients,
   3 servers), deliberately left running because it is the reference for the
   18.5 MB Go per-client figure in `docs/benchmarks/memory.md`. It was never signalled, stopped or
   reprofiled, and was verified intact afterwards. Its ~0.1–0.2 idle load and its share of the
   NIC are part of every number here, for both implementations equally.
7. **No port-range scenario in this session.** 11.3's four-pair `conn 4` run over UDP
   29910–29913 has not been re-taken, so it carries 11.3's provenance caveat still.
8. **Neither host was touched outside the lab.** Both ended with `lab.py cleanup` reporting
   `host matches baseline`, verified against baselines taken at 22:01Z.

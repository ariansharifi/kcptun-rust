### ⚠ Validity caveat: the Rust *server* binary is not provably this tree's build

**Read this before quoting any number below.** `lab.py` records each end's deployed artefact in
the run's `state.json`, read from `deploy.sh`'s `bin/BUILD.txt` during preflight. The client
field is filled on every run: `host x86_64, rust x86_64-unknown-linux-gnu (glibc 2.17), profile
release, go linux/amd64, rev 03afc40-dirty, deployed 2026-09-23T21:40:15Z`, and
**`server_build` is the empty string in every one of the 27 runs**: all 12 S1-bulk runs, all 9
S2-bulk runs, both S1-latency runs and all 4 runs of the four-pair port-range session (and the 2
runs of the superseded 00:13Z session besides). That is why every run section of the four detail
documents prints `server host lab-arm64 (<lab-arm64-ip>), build (not recorded)`.

Stated without softening: **the Rust server binary used in the RR and GR runs cannot be shown,
from what the runs recorded, to be a build of this tree.** Its identity rests on an out-of-band
inspection rather than on the run record: `~/kcptun-lab/bin/rust/kr-server` on lab-arm64 was a
static aarch64-musl file from 15:02Z, sha256 `45278efb…`, 2 499 000 bytes, with **no `BUILD.txt`
beside it**, which is precisely why the field is empty. The file was left in place and held open
by the soak that was still running there; it could not be replaced without disturbing that run.
It is **still that binary** in the four-pair port-range session below: by the time that one ran
lab-arm64 was idle and could have been redeployed, and it deliberately was not, because
redeploying mid-document would have put the port-range RR and GR runs on a different server
artefact from every other number here. From its lineage the deployed binary **contains V18**
(12.2a, tx-channel backpressure) but **not 12.3b/12.3c** (the memory work: release-after-burst,
and the contiguous receive batch that took a session from 435 kB to 55 kB). So on this rung:

- **goodput, latency and the retransmit counters are comparable** on both sides: the two
  implementations demonstrably interoperated over a real 131 ms path, and no wire behaviour here
  turns on which Rust revision the server is;
- **the server's RSS is not the shipping build's**, and the numbers below show exactly the
  difference 12.3c makes, because the *client* end is the current build and the server end is not;
- **every RR and GR figure therefore carries an unquantified revision risk.** Nothing in the
  counters suggests it is large, but it is not measured and it is not provable from what was
  recorded.

The result is kept rather than discarded: a 27-run interleaved session over a real 131 ms path is
expensive, and the interop and latency-under-load findings do not depend on the server's
revision. What would close the caveat is a re-run against a redeployed, `BUILD.txt`-stamped
server; whether to spend that is a decision recorded outside this file. Until then **no number
here may be presented as a clean measurement of this tree**, and the fix for the tooling side is
simply that a WAN run should refuse to start, or shout, when `server_build` comes back empty.

**The tooling side is fixed (12.0).** `deploy.sh` now writes a `BUILD.txt` beside *every* set of
binaries it copies (`bin/rust/`, `bin/go/`, `bin/lab/`) carrying the full commit, the libc, the
target triple and the sha256 of each file, and `lab.py run` resolves the stamp for the artefact
each end will actually execute, hashes that binary on the host, and **refuses to start** unless
the two agree. The exact state this session ran in (an aggregate `bin/BUILD.txt` one directory up
and nothing beside `kr-server`) is now a refusal that names the deployment which would fix it.
`--allow-unprovenanced` still runs, and marks every report of that session `UNPROVENANCED`.
Nothing about the numbers below changes: only a re-run against stamped binaries closes the caveat.

### S1: the user's production profile (xor, normal, no FEC, windows 8192, mtu 1390, conn 4)

12 runs, three per pair, 60 s of iperf3 each way, interleaved. Medians.

| | GG | RR | GR | RG | RR/GG |
|---|---:|---:|---:|---:|---:|
| **up** (client sends) Mbit/s | **354** | **266** | 349 | 290 | **0.75×** |
| **down** (server sends) Mbit/s | **142** | **198** | 192 | 145 | **1.40×** |
| client RSS peak, MB | 82 | **23** | 84 | 22 | 0.28× |
| server RSS peak, MB | 84 | 42 | 41 | 89 | 0.50× |
| client CPU s (both directions) | 98 | 88 | 101 | 83 | 0.90× |
| client peak CPU, % of its one core | 94 | 85 | 93 | 87 | - |

Throughput follows **whichever end is sending**, and the receiving implementation barely matters:
Go-as-sender gives 354/349 up and 142/145 down; Rust-as-sender gives 266/290 up and 198/192 down.
So there are two separate results here, not one.

The retransmit counters, as rates rather than totals. kcp-go accumulates
`RetransSegs = LostSegs + FastRetransSegs + EarlyRetransSegs`
(`reference/kcptun/vendor/github.com/xtaci/kcp-go/v5/kcp.go`, the "counter updates" block of
`flush`) and Rust matches it, so all three components are quoted here and the total is fully
attributed with no remainder. Each cell is the **median over that pair's repetitions of each
run's own ratio**, which is why the three components do not add to the total to the last digit;
within any one run's totals (in the detail doc) they add exactly.

| | GG | RR | GR | RG |
|---|---:|---:|---:|---:|
| client segments sent | 3.32 M | 2.79 M | 3.25 M | 3.01 M |
| client **retransmitted** (`RetransSegs`), % of sent | **3.2** | **9.3** | 2.8 | 8.5 |
| …of which RTO-driven (`LostSegs`), % | 2.8 | 9.0 | 2.5 | 8.2 |
| …of which fast (`FastRetransSegs`), % | 0.30 | 0.17 | 0.35 | 0.20 |
| …of which early (`EarlyRetransSegs`), % | 0.01 | 0.04 | 0.00 | 0.02 |
| server **duplicates received** (`RepeatSegs`), % of received | **3.1** | **9.2** | 2.7 | 8.3 |
| server segments sent | 1.78 M | 2.18 M | 1.95 M | 2.03 M |
| server **retransmitted** (`RetransSegs`), % of sent | **37.9** | **23.2** | 27.4 | 34.9 |
| …of which RTO-driven (`LostSegs`), % | 29.1 | 16.6 | 21.0 | 25.2 |
| …of which fast (`FastRetransSegs`), % | 10.0 | 6.5 | 6.8 | 9.4 |
| …of which early (`EarlyRetransSegs`), % | 0.39 | 0.09 | 0.12 | 0.23 |
| client duplicates received, % of received | 21.3 | 14.9 | 17.6 | 19.0 |
| `FECRecovered` / `FECErrs` / `InErrs` / `KCPInErrors` | 0 | 0 | 0 | 0 (S1 has no FEC) |

Early retransmission is a rounding error on every pair and in both directions, at most 0.39 %
of segments sent, so nothing below turns on it. It is quoted rather than left as an
unexplained remainder inside `RetransSegs`.

**The client-side retransmissions are almost entirely spurious.** On every pair the receiver's
duplicate rate tracks the sender's retransmit rate to within a tenth of a percent (3.2 → 3.1,
9.3 → 9.2, 2.8 → 2.7, 8.5 → 8.3): the segment that was retransmitted had already arrived. Both
implementations do this at 131 ms with a 8192-packet window: **Rust does it three times as
often**, and that accounts for most of the 25 % it gives away on the upload.

It is not a CPU ceiling. The Rust client used **less** CPU than the Go client (88 s vs 98 s, peak
85 % vs 94 % of the single core) and its whole-run CPU per gigabyte moved was the same (25.1 vs
26.1 s/GB). It sent fewer segments and wasted a larger fraction of them.

In the other direction the same code is **better** than Go: sending from lab-arm64, Rust
retransmits 23.2 % against Go's 37.9 % on a path that is genuinely lossy for both, and delivers
1.40× the goodput at a whole-run 26.3 s/GB on the server against Go's 29.8.

**The confound, stated plainly:** direction and host are not separable in this rung. "Client
sends" is also "a 1-vCPU x86_64 box sends into a clean direction", and "server sends" is also "a
2-vCPU aarch64 box sends into a lossy direction". Which of those Rust's deficit belongs to cannot
be settled here. The 5.1 ms and 56.7 ms rungs (both between 1-vCPU x86_64 boxes) are what would
separate them, and they are exactly the rungs this session could not run.

### S2: kcptun's defaults (aes, fast, FEC 10/3, comp, sndwnd 128 / rcvwnd 512)

9 runs (GG ×3, the others ×2: the session aborted before its last three; see the caveats).

| | GG | RR | GR | RG | RR/GG |
|---|---:|---:|---:|---:|---:|
| up Mbit/s | 8.54 | 8.86 | 8.45 | 9.75 | **1.04×** |
| down Mbit/s | 8.53 | 8.90 | 9.75 | 8.46 | **1.04×** |
| client retransmitted, segments | 546 | 608 | 258 | 1 464 | - |
| server retransmitted, segments | 1 107 | 516 | 822 | 852 | - |
| `FECRecovered` | 0 | 0 | 0.5 | 0.5 | - |
| client RSS peak, MB | 30 | **7** | 30 | 7 | 0.23× |

**This is the natural experiment for the S1 result.** S2 is the same two hosts, the same path, the
same evening, and a 128-packet send window instead of 8192. At 131 ms that window is its own
limit (128 × ~1.3 kB / 0.131 s ≈ 10 Mbit/s), which is exactly what both implementations produce,
and **the difference disappears: 1.04× in both directions**, with retransmissions in the hundreds
rather than the hundreds of thousands.

So whatever costs Rust 25 % on the S1 upload is a property of **a deep send window at a long
RTT**, not of the crypto, the framing, the syscalls or the host. That is the regime V18's
backpressure governs, and it is where the next measurement should look.

`FECRecovered` is **almost** 0: the table's cells are medians, and the 0.5 for GR and RG is
where one run each recovered a segment. Over all nine S2 runs FEC reconstructed **three
segments**, one each on GR r1, RG r1 and GG r3, all on the client side
([`11.3-wan-x86-3-arm64-s2-bulk.md`](11.3-wan-x86-3-arm64-s2-bulk.md)); two of the three are mixed
pairs, and 11.3b at 95.3 ms recovered 16 segments of which every one was on a mixed pair (5 on a
Go client from a Rust server's parity, 11 on a Rust client from a Go server's). So cross-
implementation FEC reconstruction does happen and works both ways. Three segments in nine runs
is otherwise nothing: at 8.5 Mbit/s this path loses almost nothing, so FEC 10/3's 30 % of parity
bought nothing here. That is not evidence against FEC: it is evidence that this rung, at this
rate, is not the place to test it. The 46.3 ms jittery rung is.

### S1 latency under load: the 10-minute probe

A 64-byte request/response probe for 600 s with a competing bidirectional bulk flow inside the
same tunnel. One run per pair.

| | GG | RR | RR/GG |
|---|---:|---:|---:|
| ping p50 | 163 ms | **136 ms** | 0.83× |
| ping p90 | 241 ms | **189 ms** | 0.79× |
| ping p99 | 435 ms | **337 ms** | 0.77× |
| ping max | 805 ms | **540 ms** | 0.67× |
| competing bulk | 229 Mbit/s | **279 Mbit/s** | 1.22× |
| errors | 0 | 0 | - |
| client retransmitted segments (`RetransSegs`) | 2 937 533 | **1 077 205** | 0.37× |
| …RTO-driven (`LostSegs`) | 2 729 363 | **1 056 716** | 0.39× |
| …fast (`FastRetransSegs`) | 201 310 | 19 593 | 0.10× |
| …early (`EarlyRetransSegs`) | 6 860 | 896 | 0.13× |
| client RSS peak | 85 MB | **27 MB** | 0.32× |
| server RSS peak | 89 MB | 108 MB | 1.21× _(pre-12.3 build)_ |

**This is the V18 result the rung was run for**, and it is unambiguous: with a bulk flow and an
interactive stream sharing one tunnel over a 131 ms path, Rust is faster at *every* percentile,
including the tail, where it removes a third of the worst case, **and** carries 22 % more bulk
while doing it, while retransmitting 63 % less.

The contrast with the S1 iperf3 upload is the interesting part. A single unidirectional TCP
stream from the 1-vCPU client is where Rust loses; a mixed, bidirectional workload, which is
what a tunnel actually carries: is where it wins, on both axes at once. A report that quoted
only one of those would be misleading, so both are here.

### S1 with a port range (`conn 4` spread over UDP 29910–29913)

All four pairs, one run each, interleaved: session `20260924T011854Z`, 01:19–01:33Z. The same
four sessions as S1, over four ports instead of one. A **mixed** pair matters here more than
anywhere else in the set: which session lands on which port of the range is the client's choice
and the server has to follow it, so GR and RG are what demonstrate that the two implementations
agree about the arrangement rather than each merely being self-consistent.

| | GG | RR | GR | RG | RR/GG | S1 single-port, for reference |
|---|---:|---:|---:|---:|---:|---|
| up Mbit/s | 385 | 291 | 396 | 313 | 0.76× | 354 / 266 → 0.75× |
| down Mbit/s | 142 | 202 | 199 | 153 | 1.42× | 142 / 198 → 1.40× |
| client retransmitted (`RetransSegs`) | 99 702 | 247 492 | 66 182 | 241 683 | 2.48× | 105 068 / 259 635 → 2.47× |
| …RTO-driven (`LostSegs`) | 92 942 | 243 289 | 57 575 | 237 604 | 2.62× | 92 531 / 252 469 → 2.73× |
| …fast + early | 6 760 | 4 203 | 8 607 | 4 079 | 0.62× | 10 174 / 6 033 → 0.59× |
| server duplicates received (`RepeatSegs`) | 93 067 | 245 648 | 63 786 | 238 169 | 2.64× | - |
| client RSS peak, MB | 80 | **22** | 84 | 22 | 0.28× | 82 / 23 → 0.28× |
| server RSS peak, MB | 78 | 45 | 42 | 78 | 0.58× | 84 / 42 → 0.50× |
| `FECRecovered` / `FECErrs` / `InErrs` / `KCPInErrors` | 0 | 0 | 0 | 0 | - | 0 everywhere (S1 has no FEC) |

**The mixed pairs work, and they land on the single-port result rather than on something of their
own.** Throughput follows whichever end is sending, exactly as on one port: a Go sender gives
385/396 up and a Go server 142/153 down; a Rust sender gives 291/313 up and a Rust server 202/199
down. The server's `RepeatSegs` tracks the client's `RetransSegs` to within 1–7 % on every pair
(99 702 → 93 067, 247 492 → 245 648, 66 182 → 63 786, 241 683 → 238 169), mixed pairs included,
the same near-identity the single-port table shows, and the same conclusion, that the upload
retransmissions are mostly spurious. What a range the two sides disagreed about would produce is
`KCPInErrors`, stuck sessions or missing bytes, and there are none in any of the four runs.

**The port range changes nothing**, which is the result one wants from it: it is a deployment
option, not a performance one. In particular the S1 upload deficit (0.76× here against 0.75× on
one port) is reproduced unchanged, so it is not an artefact of how the four `conn` sessions are
spread.

Two things to hold against this table. It is **one run per pair**, so a single noisy minute moves
a cell; and **GG ran first, on a client whose load average was 0.00**, while RR, GR and RG each
started while the previous run's load was still decaying (0.64–1.20 on the client, 1.05–1.17 on
the server): `lab.py` preflights the load once per session, not once per run. That ordering
flatters GG a little in every session in this document, which is one more reason the bulk tables,
with three interleaved repetitions each, are the ones to argue from.

An earlier two-pair session (`20260924T001328Z`, GG and RR only: 354 / 252 up, 145 / 198 down) was
superseded by this one and is not quoted above. Its numbers agreed with these within the session
spread, and it is left in `lab-runs/` rather than folded in: two sessions an hour apart are not
one session, which is the caveat this whole document turns on.

## Caveats

1. **Superseded as evidence** by [11.3b](11.3b-wan-matrix.md) (the banner at the top): the
   headline here is not confirmed, the retransmission behaviour is.
2. **Within-session only.** Stated at the top, repeated here because it is the one that matters.
3. **The Rust server binary is not provably this tree's build** (the validity caveat above).
   `server_build` is empty in all 27 `state.json` files, so the RR and GR server end is
   attributed out of band (a static aarch64-musl file with no `BUILD.txt`) and not by the run
   record. Goodput, latency and retransmit counters stand as an interop result; the server-side
   RSS column is an older build's, and every RR/GR figure carries an unquantified revision risk.
4. **Neither host's socket-buffer ceiling was recorded.** `socket_buffer_limits` did not exist in
   `lab.py` at this session's revision (`03afc40`), and D32 later showed that a stock
   `net.core.rmem_max` against S1's `-sockbuf 8388608` silently decided three cells of the 11.2
   matrix. Whether the client here was clamped cannot be established from the record.
5. **Direction and host are confounded** on this rung (above).
6. **The bitrate cap.** `iperf3 -b` is a guard rail against saturating lab-arm64's NIC, not part of
   the measurement. The first attempt used 60 Mbit/s, which *bound*: every pair reported exactly
   60.0 Mbit/s both ways, and was discarded and re-run; 200 Mbit/s still bound on the upload; the
   committed scenarios use 400 Mbit/s, which is above the ~354 Mbit/s a single core reaches here,
   so it never binds. If a future rung reports a flat 400.0, the cap has become the measurement
   again and the run is void.
7. **The S2 session lost its last three runs.** Its tenth run failed to start the reverse iperf3
   test with `the server is busy running a test`: one `iperf3 -s` serves both directions, and at
   131 ms the forward test was still draining the tunnel when the reverse one dialled 70 s later.
   `lab.py` aborts a scenario on a failed start (a failure to start is usually systematic, and
   continuing would hide it), so GG has three repetitions and the other pairs two. The scenarios
   now leave 95 s, and the affected runs are the ones already collected: nothing was retried into
   the same table.
8. **The latency probe is GG and RR only, no mixed pair.** It is a 600 s run per pair and the
   competing-bulk arrangement is the same code path the bulk scenarios exercise with GR and RG,
   so interop is covered there; but nothing in this document shows a mixed pair under the
   latency-under-load workload, and the V18 conclusion below rests on GG against RR. The port
   range **does** have all four pairs (re-run as a four-pair interleaved session for exactly this
   reason), and every pair there is **one run**, as is every pair of the latency probe. These are

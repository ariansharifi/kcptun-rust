# 11.5 — failure modes, Go beside Rust

Ten ways of breaking a running tunnel, each one run against **both implementations** on the same
host, in the same namespace lab, with the same flags and the same fault at the same offset. The
question 11.5 asks is not "does the Rust port recover" but "does it recover the way Go does, by
the same mechanism, in the same time", so every case below has a GG row and an RR row and the two
are meant to be read against each other rather than against an absolute.

| | |
|---|---|
| host | `lab-x86-3` (Ubuntu 24.04, x86_64, 1 vCPU, 961 MB) — the netns lab, `kr-cli` ↔ `kr-srv` |
| config | **S1**, the user's production profile (xor, no FEC, `mode normal`, windows 8192, smux 16M/16M, mtu 1390, `nocomp`, `conn 4`) |
| driver | `tools/lab/failure.py` (Step 11.5), `tools/lab/failure.py report <session>...` |
| generated tables | [`11.5-failure-modes-tables.md`](11.5-failure-modes-tables.md) — every case, every check, with the reason each bound was chosen |
| `net.core.rmem_max` | 8388608 on this host, so S1's `-sockbuf 8388608` is honoured in full and D32's clamp does not apply (checked before the campaign, and recorded in every `state.json`) |
| sessions | `20260924T212244Z-failure` (16 runs, 8 cases × GG/RR) and `20260924T220251Z-failure` (the two `--tcp` cases, RR), 2026-09-24, one after the other on an otherwise idle box |

## How a recovery time is measured

A `kr-pingpong ping` runs through the tunnel for the whole of each case — one connection, 64-byte
`ECHO` exchanges, 200 ms apart — writing one CSV row **per second**. At fixed offsets the driver
stops a process, starts it again, or switches the netem profile, and records the wall-clock time
of each event in the run's `state.json`. The CSV is therefore a second-by-second record of when
traffic stopped and when it came back, and every number below is arithmetic over it rather than a
stopwatch:

- **outage** — from the last second that carried a completed request before the fault to the
  first that carried one after it;
- **recovery** — from the *repair* (the restart, or the moment the path came back) to that first
  post-repair second.

`ping` has no per-request timeout, deliberately: a request on a session whose peer has died hangs
until smux gives up, so the gap in the CSV is the tunnel's own recovery time and not a timeout the
workload chose. A second is only counted as "after" an event when the whole second is after it,
which can over-state a recovery by up to one second and can never under-state an outage.

## The result: 18 of 18 runs met every check, and the two implementations agree everywhere

| case | injected | Go → Go | Rust → Rust |
|---|---|---|---|
| **server restart** (SIGTERM) | stopped at t+20 s, started again at t+24 s | recovery **35.9 s**, outage 40 s, 1 error, 1 reconnect | recovery **36.0 s**, outage 41 s, 1 error, 1 reconnect |
| **server SIGKILL** | killed at t+20 s, started again at t+24 s | recovery **36.0 s**, outage 41 s | recovery **36.7 s**, outage 42 s |
| **client SIGKILL** | killed at t+20 s, started again at t+24 s | recovery **1.9 s**, 18 failed attempts | recovery **1.1 s**, 17 failed attempts |
| **blackhole 45 s** | netem `loss 100%`, t+20 s → t+65 s | outage **48 s**, recovery 1.9 s after the path returned | outage **47 s**, recovery 1.6 s |
| **`autoexpire 30 scavengettl 15`** | nothing — rotation under load | 3 rotations, longest gap **1.0 s**, 732 requests | 3 rotations, longest gap **1.0 s**, 735 requests |
| **port range `29904-29907`** | nothing — rotation across four ports | 3 rotations, 2 distinct ports, 0 out of range | 3 rotations, 2 distinct ports, 0 out of range |
| **target refuses** | `-t` at a closed port | 176 failed dials in 45 s, median **0.0 s** apart | 178 failed dials, median **0.0 s** |
| **target blackholed** | `-t` at an address whose SYNs are dropped | 7 failed dials in 75 s, median **10.0 s** apart | 7 failed dials, median **10.0 s** |
| **`--tcp` restart** | as above, over fake TCP | — (DECISIONS V22) | recovery **36.1 s**, outage 40 s |
| **`--tcp` blackhole** | as above, over fake TCP | — (V22) | outage **47 s**, recovery 1.9 s, 2 × `re-connecting:` |

Every bound each of those was checked against, and why it was chosen, is in
[the generated tables](11.5-failure-modes-tables.md). Not one collected log of the 18 runs matched
an error marker, and `lab.py cleanup` reported `host matches baseline` afterwards.

### 1. A dead server costs 36 seconds, and the mechanism is the one 09.3 named

Both implementations noticed a dead peer at the same moment and recovered by the same route, to
within 0.7 s of each other across four runs (35.9 / 36.0 / 36.0 / 36.7 s). That is not luck: the
fault is injected at the same offset in every run, so both see the same phase of smux's keepalive
window, which is exactly what makes the comparison a comparison.

**The plan's ~60 s is the top of a band, not a constant.** smux's `KeepAliveTimeout` is its own
30 s and its keepalive goroutine closes the session on the first 30 s tick that finds no data
since the previous one. A tick that lands while traffic is still arriving clears the flag and
lets the session live, so where the death falls inside that window decides the answer: just after
a tick gives ~60 s, just before it gives ~30 s. 09.3 measured 64.89 s and corrected the plan's
30 s; this campaign measures 36 s at the other end of the same band. **30–60 s is the honest
statement**, and both implementations sit at the same point in it.

**`re-connecting:` never appeared in a client log of any of the 16 UDP-transport runs** (18 client
logs, counting the second generation the two client-SIGKILL runs start). 09.3 corrected the plan's
bullet on the strength of reading the source — that loop runs only when `createConn()` fails, and
dialling UDP does not fail — and this is that correction confirmed on a real path, for both
implementations, as an explicit absence check rather than a remark.

**The `--tcp` transport is the exception, and it is one the campaign found rather than assumed**;
§5 has it. Every run's `re-connecting:` count is now a column of
[the generated tables](11.5-failure-modes-tables.md), so the two transports' different mechanisms
are asserted side by side rather than left to a reader's `grep`.

What does appear, exactly twice in each restart run, is the client naming its new session:

```
2026/09/25 00:23:12 main.go:473: smux version: 2 on connection: 0.0.0.0:52548 -> 10.200.0.2:29904
2026/09/25 00:24:12 main.go:473: smux version: 2 on connection: 0.0.0.0:34730 -> 10.200.0.2:29904
```
```
2026/09/25 00:26:14 main.rs:766: smux version: 2 on connection: 0.0.0.0:33221 -> 10.200.0.2:29904
2026/09/25 00:27:15 main.rs:766: smux version: 2 on connection: 0.0.0.0:59384 -> 10.200.0.2:29904
```

Same message, same count, 60 and 61 seconds apart: the keepalive closes the dead session, the
scavenger reports it, and the next accepted connection finds `IsClosed()` and dials a new one.
`ActiveOpens` on the client and `PassiveOpens` on the restarted server agree with the logs in both
arms (2 and 3).

A SIGKILLed server is indistinguishable from a blackholed one — no FIN, nothing on the wire — and
recovers identically. A SIGKILLed *client* is a different shape and both recover in 1–2 s: there
is nothing to time out, the workload's connection is refused until the new listener is up, and the
new client dials a fresh conv.

### 2. The blackhole re-dials **during** the outage

In both arms the second session was dialled 60–61 s after the first, which is **inside** the 45 s
blackhole. Nothing about that fails: dialling UDP does not fail, so the client creates the new
session against a path that is still dropping everything, and the first exchange completes 1.6 s
(Rust) / 1.9 s (Go) after netem is set back to `clean`. The 45 s blackhole shows up as a 47–48 s
outage, the extra being the detection at the start.

### 3. Rotation is a closure, not a migration — and it costs one second

`-autoexpire 30 -scavengettl 15` rotated three times in 150 s in both arms, and the client logged
`scavenger: session closed due to ttl:` three times and `scavenger: session normally closed:` zero
times in *both* — identical strings, identical counts. That is the shape of the mechanism: the
scavenger closes the expired session, which ends the stream on it, the workload reconnects, and
the next accepted connection dials a fresh session. The longest gap in traffic either arm suffered
was **1.0 s**, so a rotation costs one reconnect and no dropped work.

A port-range server (`29904-29907`) behaves exactly the same way while hopping across the range.
`createConn()` picks the port afresh out of `[MinPort, MaxPort]` on every dial
(`reference/kcptun/client/dial.go:56`), so the case checks that **every dial landed inside the
range** — deterministic, where "more than one distinct port" would be a coin toss at four dials —
and reports the distinct count beside it. Both arms dialled two of the four ports: Go
29906/29904/29904/29904, Rust 29907/29906/29906/29906, nothing outside the range in either.
`client_active_opens ≥ 2` is a floor on dials and *not* evidence of rotation, incidentally: under
`conn 4` the second accepted connection dials a second session on its own
(`reference/kcptun/client/main.go:429-437`). The `scavenger: … due to ttl:` count is the
discriminator, and both cases check it.

### 4. A refused target and an unreachable one are two different failures, in both

A closed port returns an RST: 176 (Go) and 178 (Rust) failed exchanges in 45 s, the median gap
between them 0.0 s — the workload's own 250 ms pause is the only delay. An address whose SYNs are
dropped costs Go's `const dialTimeout = 10 * time.Second`
(`reference/kcptun/server/main.go:488`): **exactly 7 failed exchanges in 75 s in both arms, median
gap 10.0 s**. The Rust server honours that constant to the tenth of a second.

### 5. `--tcp` survives a restart and a blackhole, and leaves nothing behind

The fake-TCP transport recovers in 36.1 s from a server restart and 1.9 s after a 45 s blackhole —
the same numbers as UDP, which is what one would expect of KCP above a different datagram carrier.
**The numbers match; the mechanism does not.** `--tcp` is the one transport on which
`createConn()` can fail: `dial()` there performs a real `tcpraw.Dial()` and TCP connect
(`reference/kcptun/client/dial.go:67`), and while netem is dropping everything that connect
returns `ENETUNREACH`. `waitConn`'s retry loop (`reference/kcptun/client/main.go:505`) is
therefore genuinely the recovery mechanism here, and it logged twice during the 45 s blackhole:

```
2026/09/25 01:07:22 main.rs:805: re-connecting: dial(): tcpraw.Dial(): dial tcp 10.200.0.2:29904: connect: no route to host
2026/09/25 01:07:25 main.rs:805: re-connecting: dial(): tcpraw.Dial(): dial tcp 10.200.0.2:29904: connect: no route to host
```

The wrap chain is Go's own — `errors.Wrap(err, "tcpraw.Dial()")` inside `dial()`, printed by
`log.Println("re-connecting:", err)` — so the Rust line is evidence of fidelity rather than a
deviation, and the `tcp-blackhole` case now asserts its presence the way `server-restart` asserts
its absence. (The `--tcp` *restart* logs none: the server is back four seconds later, so the next
dial succeeds first try.)

Afterwards both namespaces' `filter/OUTPUT` chains were inspected by hand on the host and were
empty, with the host's own ruleset untouched — but that is a manual observation, not an artefact
of the campaign: `failure.py` captures no iptables listing, so unlike every other claim here it
does not regenerate from `failure.py report`, and the namespaces have since been destroyed. The
rule-leak accounting that *is* asserted — including that a SIGKILLed `--tcp` end leaves exactly
one rule, as Go does — is **10.5's**, and that is where it should be read from. These two cases
run RR only: DECISIONS V22 records that the *Go* `--tcp` client carries no data at all, so a
Go-client arm would measure that bug instead of the failure mode. The `--tcp` interop matrix
itself is 10.5's.

### 6. An aside the campaign did not set out to measure

Across the eight cases that carry traffic (six of them with a Go arm — the two `--tcp` cases run
RR only), the request/response p50 through the tunnel is **1.4–1.5
ms for Rust against 2.0–2.1 ms for Go**, on the same box, in the same minute, with the same
workload. It is consistent enough to note and too narrow a workload (one connection, 64 bytes) to
conclude anything from; 11.2 and 11.3 are where latency is actually measured.

## Deviations from the plan's wording

- **`autoexpire 30 scavengettl 15`, not `60`/`30`.** The rotation period a client actually sees is
  `autoexpire + scavengettl` (the session expires, then the scavenger closes it a TTL later), so
  the plan's pair rotates every 90 s and would have shown at most one rotation in a case long
  enough to keep a 1-vCPU box busy for six minutes per arm. Halving both preserves the ratio and
  the mechanism and gives three rotations per arm to average over.
- **`re-connecting:`** is not the restart mechanism over UDP (09.3's correction, now confirmed
  live) — though it *is* the mechanism under `--tcp`, where `createConn()` really can fail. Both
  bullets of step 11.5 have been corrected to say so.
- **"smux keepalive closes the session after about 30 s"** in the blackhole bullet is the
  *interval*, not the observed close: the observed close is 40 s after the peer went silent, inside
  a 30–60 s band, in both implementations. Corrected in the step file too.


## What could not be injected, and where it is covered instead

- **A client restart reusing the same UDP source port with a new conv** ("the server replaces the
  session only on an `sn == 0` packet"). Neither implementation lets the client choose its source
  port, so the live lab cannot produce the collision; the rule itself is covered by the unit test
  `a_conv_mismatch_resets_the_session_only_when_sn_is_zero` in `crates/kcp/src/listener/tests.rs`,
  against `reference/.../kcp-go/v5/sess.go:1187` ("conversation id mismatched, only accept reset
  packet with sn == 0").
- **Half-open connections.** The workload has no half-close anywhere, by design
  (`tools/pingpong/README.md`): kcptun's half-close behaviour differs between the implementations
  where a Go peer runs `-QPP` (DECISIONS V04, V11), so a workload that ended transfers with
  `shutdown(SHUT_WR)` would measure that difference instead of the failure mode. Half-close is
  09.3's `e2e_closewait_*` cases and V11's business.
- **A Go `--tcp` client.** DECISIONS V22: it carries no data at all, which 10.5 reproduced. The
  two `--tcp` cases therefore run RR (and can run RG), and what they add to 10.5 is what a restart
  and a blackhole do to the fake-TCP transport, not another interop matrix.

## Reproducing

```sh
tools/lab/failure.py --host lab-x86-3 cases
tools/lab/failure.py --host lab-x86-3 run --pairs gg,rr
tools/lab/failure.py --host lab-x86-3 run --case tcp-server-restart --case tcp-blackhole --pairs rr
tools/lab/failure.py report <session-1> <session-2> \
    --out docs/lab-results/11.5-failure-modes-tables.md
```

The two `run` invocations write **two** session directories (the `--tcp` cases need `--pairs rr`,
so they cannot share one), which is why `report` takes several and concatenates them: it groups by
case regardless of which session a run came from. The published 18-run table is
`20260924T212244Z-failure` (16 runs) and `20260924T220251Z-failure` (2) in that order.

The driver never touches the host except through the guarded helpers of tools/lab/README.md: processes
are started and stopped by PID file after `/proc/<pid>/exe` is verified (so "kill the server" can
never mean somebody else's server), netem only ever touches our own veths, and no port below 4000
is used. `tools/lab/failure_test.py` covers the timeline and the arithmetic against a fake host
and runs inside the cargo gate.

# 11.2 — the netem impairment matrix, Go against Rust

Session of **2026-09-24**, on **lab-x86-2** (Ubuntu 24.04, x86_64, **1 vCPU**, 1967 MB), driven
from the laptop by `tools/lab/matrix.sh` → `tools/lab/lab.py`. lab-x86-2 is the only lab host
that has never carried a tunnel (tools/lab/README.md), so nothing of production traffic shared its core
with these runs; **lab-arm64, which carries the live production mesh, was not touched.**

Binaries: `host x86_64, rust x86_64-unknown-linux-gnu (glibc 2.17), profile release, go
linux/amd64, rev 7373bae` — **glibc, not musl**, because D07 is settled and glibc is what the
released Linux artifacts are. The Go side is `reference/bin/client_linux_amd64` and
`server_linux_amd64`, the pinned reference binaries, copied byte for byte. Every run records that
line in its `state.json`, and `lab.py` now **refuses to start** on a host that cannot produce it.

Generated tables: [`11.2-netem-matrix-tables.md`](11.2-netem-matrix-tables.md) (the campaign) and
[`11.2-netem-matrix-sockbuf.md`](11.2-netem-matrix-sockbuf.md) (the controlled re-run described
below). This file is what they mean.

> **Read this first.** Both tunnel ends, the workload and the workload's target run **on the same
> one-vCPU host**, joined by a veth pair across two network namespaces. These numbers measure
> **protocol behaviour and the two implementations' relative standing, not absolute throughput**
> (tools/lab/README.md).

## What was run

- **Workloads.** `bulk-iperf3`: 30 s of iperf3 forward (`up`), then 30 s reverse (`down`), one
  TCP stream through the tunnel. `latency`: 30 s of 64-byte request/response (`lat64`) on an idle
  tunnel, then 30 s of the same probe while a two-stream `pingpong bulk` flow competes
  (`lat64load`). `bulk-capped`: `bulk-iperf3` with the offered rate capped at 250 Mbit/s.
- **Pairs.** GG, RR, GR, RG (client implementation first), **interleaved** inside every cell —
  each repetition runs all four pairs before any pair runs twice — so drift in the host's own
  conditions reaches Go and Rust equally.
- **Repetitions.** 3 per pair per cell; every figure is the **median** of those 3.
- **Impairment.** netem on the egress of **both** our veths, so a profile's delay and loss apply
  in each direction: `wan50` (`delay 50ms 5ms loss 0.1%`) is ≈100 ms RTT and ≈0.2 % round-trip
  loss, `lossy2` (`delay 80ms 8ms loss 2% reorder 1% 50%`) ≈160 ms and ≈4 %, `lossy10`
  (`delay 80ms loss 10%`) ≈160 ms and ≈19 %. `ratelimited` is `delay 40ms rate 100mbit`; `burst`
  is `delay 60ms loss gemodel 1% 10% 70% 0.1%` — Gilbert-Elliott bursts at **≈120 ms RTT**, which
  is what its numbers have to be read against when they sit beside `wan50`'s 100 ms and
  `lossy2`/`lossy10`'s 160 ms.
- **Configurations.** S1 the user's production profile (xor, no FEC, `mode normal`, windows 8192,
  smux 16M/16M, mtu 1390, nocomp, `conn 4`); S2 kcptun's defaults (aes, FEC 10/3, `fast`,
  windows 128/512); S3 `fast3` + aes-128-gcm + FEC 10/3, windows 1024; S4 salsa20 without FEC,
  windows 1024.
- **16 cells, 192 runs.** S1 over all seven profiles, plus the capped control and three latency
  cells; S2 over `clean`, `wan50`, `lossy10`; S3 and S4 over `lossy10`. The rest of the 28-cell
  grid was not run — the lab is serial on one host at ~16 min a cell — and the runbook at the end
  is what completes it.

## The result that changes how the rest is read: the host's socket-buffer ceiling

`setsockopt(SO_RCVBUF)` is **silently clamped** to `net.core.rmem_max`. lab-x86-2 has the stock
**212992** (208 KiB); **lab-arm64, the box this deployment actually resembles, is tuned to
8388608 / 67108864** (tools/lab/README.md). So the S1 profile's `-sockbuf 8388608` bought a 208 KiB
receive buffer on this host — 40× less than it asked for — and with `-sndwnd 8192` a single flush
can offer thousands of packets into it.

Measured directly, from `/proc/net/snmp` inside both namespaces, around **one 65 s S1 `lossy10`
run** of each pair:

| ceiling | pair | datagrams delivered (client ns) | dropped to `UdpRcvbufErrors` | share dropped |
|---|---|---:|---:|---:|
| 212992 (default) | GG | 294,834 | 95,133 | 24.4 % |
| 212992 (default) | RR | 239,177 | **223,293** | **48.3 %** |
| 8388608 (lab-arm64's) | GG | 396,602 | **0** | 0 % |
| 8388608 (lab-arm64's) | RR | 404,578 | **0** | 0 % |

`UdpInErrors` equalled `UdpRcvbufErrors` exactly in every sample: every one of those losses was
the receive buffer overflowing, not a checksum, not a closed port. And Rust overflowed it 2.3×
as often as Go, which is what a 347×-faster `flush` (D29) does with a 8192-segment window — it
can put the burst on the wire much more quickly than Go can, and a 208 KiB buffer cannot hold it.

**Every cell that failed 11.2's acceptance criterion passes once the buffer is what the profile
asked for.** Same host, same binaries, same scenario, only `net.core.rmem_max` changed
(a temporary sysctl under tools/lab/README.md rule 5, restored afterwards):

| S1 cell | RR/GG at 212992 | RR/GG at 8388608 |
|---|---:|---:|
| `clean` up / down | 0.86× / 0.80× | **1.45× / 1.43×** |
| `lossy10` up / down | 0.86× / 0.80× | **1.09× / 1.11×** |
| `burst` up / down | 0.90× / 0.97× | **1.25× / 1.27×** |

Rust's retransmitted share of `OutSegs` on `lossy10` falls from 45.7 % to 11.2 % (Go: 30.6 % to
15.6 %) and both implementations get much faster. **Nothing was tuned in either implementation
and no flag of either was changed**; the host was given the buffer the configuration requests.

`lab.py` now reads both sysctls into every run's `state.json` and warns at preflight when a
scenario's `-sockbuf` exceeds them, so this cannot silently happen again. tools/lab/README.md records
it.

## The `clean` cell, and why an uncapped unimpaired run cannot be read as a protocol result

Beyond the buffer, `clean` has a second problem: **every process in the box is fighting for one
core.** Summed over `cli`, `srv` and `tgt` (and `iperf3 -c` is not even sampled) a `clean` run
uses **82–84 % of the single CPU for every pair**, Go and Rust alike, and both implementations'
tunnel processes take the same ~28 CPU-seconds out of a 70-second window. At that point goodput
is decided by behaviour *at the overload point*, which nobody deploys on.

`bulk-capped` is the same scenario with iperf3 offered 250 Mbit/s, so every pair delivers the
same bits and the interesting column becomes cost:

| clean | GG | RR | RR/GG |
|---|---:|---:|---:|
| goodput up / down, capped | 250 / 250 Mbit/s | 250 / 250 Mbit/s | 1.00× |
| tunnel CPU per delivered bit | 1.42 ms/Mbit | **0.95 ms/Mbit** | **0.67×** |
| _(uncapped, for comparison)_ | 1.59 ms/Mbit | 1.97 ms/Mbit | 1.24× |

`ratelimited` says the same thing from the other direction: with the path capped at 100 Mbit/s
both pairs deliver 65–66 Mbit/s to within 0.2 %, and Rust does it for 0.49× the CPU. On
`lossy10` and `burst` nothing is CPU-bound at all — `cli` + `srv` + `tgt` come to 15 % of the
core for RR and 42 % for GG — so those cells were never a CPU story; they were the buffer.

## The spurious-retransmission question from 11.4 — attributed

The 11.4 soak recorded **28.4 % of segments retransmitted on a path whose configured loss was
0.1 %**, with **189× more duplicates received than segments lost**, fast retransmit rather than
RTO driving it, and no Go control. The note asked for exactly this: the same counters, both
implementations, the same path. Two cells answer it.

**S1 / `wan50`** (`delay 50ms 5ms loss 0.1 %` each way, the soak's profile), client side:

| | GG | RR |
|---|---:|---:|
| retransmitted share of `OutSegs` | **35.6 %** | **36.4 %** |
| fast retransmit's share of that | 44.5 % | 62.1 % |
| `client dups / server lost` | 2.34 | 2.32 |
| `server dups / client lost` | 1.89 | 2.91 |

**S2 / `wan50`** (kcptun's defaults — small windows, which is the regime the soak's many short
streams were in), where the duplicate ratio becomes enormous for *both*:

| | GG | RR |
|---|---:|---:|
| retransmitted share of `OutSegs` | 24.5 % | 26.4 % |
| fast retransmit's share of that | 76.1 % | 77.8 % |
| `client dups / server lost` | **128×** | **86.8×** |
| `server dups / client lost` | **112×** | **79.7×** |

**Go retransmits just as much, and its duplicate ratio is higher than Rust's.** The 11.4 figure
is *faithful KCP behaviour*, not something this port invented: `mode normal` with `nc = 1` has
congestion control off, and kcp-go is exactly as aggressive as we are. The 189× of the soak sits
between these two columns, and it is Go's column that is the larger one.

**On the two impaired cells above**, the one place the two differ is the **mechanism split**:
Rust reaches a given amount of retransmission with more fast retransmit and less RTO (62 %
against 45 % on S1 `wan50`, 84 % against 61 % on S1 `lossy2`), and its `LostSegs` are
correspondingly lower — 40 k against 107 k on `lossy2`. Detecting loss from duplicate ACKs
instead of waiting out an RTO is why Rust delivers 1.47× the goodput there. Same algorithm,
reacting sooner.

**On the two high-rate cells the counters run the other way**, and the generalisation does not
survive them. S1 `lan`, client side: retransmitted share 11.1 % (GG) against **22.2 %** (RR),
`LostSegs` 40,271 against **154,398**, and fast retransmit's share *lower* for Rust (72.7 %
against 76.9 %) — RTO-driven, not duplicate-ACK-driven. S1 `clean` is the same shape at a
smaller scale: 2.22 % against 4.00 %, `LostSegs` 1,864 against 6,180. Both are cells where Rust
pushes far more into the 208 KiB receive buffer than Go does, which is the headline of this
document, and both are exactly the cells the raised-ceiling re-run would settle — but that
re-run covered `clean`, `lossy10` and `burst`, not `lan`. So `clean`'s inversion is consistent
with the buffer (at 8388608 its RR/GG goes from 0.86× to 1.45×) and **`lan`'s is unattributed**:
no `lan` cell was re-run under the raised ceiling. It is listed here rather than left out.

Note where each counter is kept, because the ratio is meaningless otherwise: kcp-go increments
`RepeatSegs` in the **receiver**'s `Input` and `LostSegs` in the **sender**'s `flush`, so the
spurious-retransmission ratio pairs one end's duplicates with the *other* end's timeouts. The
generated table does that pairing in its `… dups / … lost` rows.

**Nothing here was tuned in either direction.** That was the point of the exercise.

## D29's accepted cost, measured in the loss storm

D29 made `flush()` 347× faster in the case it can skip and **26–30 % slower on the scan it
cannot**, and reasoned that a sustained loss storm pays that penalty on every flush. `lossy2` and
`lossy10` are that storm. End to end, on a real kernel, the penalty never surfaces:

| profile (S1) | GG ms/Mbit | RR ms/Mbit | RR/GG |
|---|---:|---:|---:|
| clean (capped, equal load) | 1.42 | 0.95 | 0.67× |
| lan | 3.11 | 2.14 | 0.69× |
| wan50 | 8.85 | 4.22 | 0.48× |
| **lossy2** | 10.7 | 4.10 | **0.38×** |
| **lossy10** | 7.05 | 3.07 | **0.44×** |
| burst | 6.53 | 2.88 | 0.44× |
| ratelimited (equal goodput, 1.00×) | 6.74 | 3.32 | 0.49× |

The Rust tunnel is *relatively cheapest* exactly where D29 feared it would be dearest. Go's cost
per delivered bit rises steeply as the path degrades (1.42 → 10.7 ms/Mbit) while Rust's roughly
quadruples from a much lower base (0.95 → 4.10), so the ratio improves rather than decays. The
same holds under S2, S3 and S4 (0.63× on S3 `lossy10`).

**What this does and does not settle.** It settles the deployment question — D29 costs nothing
observable against Go under sustained loss, including on the profiles chosen to be worst for it.
It does *not* isolate the 26–30 %: that is a Rust-against-Rust figure, and the shipped binaries
have no switch for `flush_scan.enabled` (it lives behind the `internals` Cargo feature, for the
benches and the D25 oracle). A direct measurement needs a criterion bench whose `snd_buf`
segments are all **due** — the existing `kcp/flush` bench fills the ring with far-future
`resendts`, i.e. precisely the case D29 *can* skip, so it measures the 347× and not the 1.3×.
That bench, and the N1 numbers D29 still lists as outstanding, belong to Step 12.

## Latency

`lat64` is the idle tunnel, `lat64load` the same probe with a competing bulk flow over the same
tunnel. Lower is better, so a ratio below 1 is Rust ahead. `comp` is what that competing flow
carried while the probe ran.

| S1 | probe / metric | GG | RR | RR/GG |
|---|---|---:|---:|---:|
| clean | lat64 p50 | 0.26 ms | 0.15 ms | **0.58×** |
| clean | lat64 p99 | 0.39 ms | 0.22 ms | **0.58×** |
| clean | lat64load p99 | 66.7 ms | 20.4 ms | **0.31×** |
| clean | comp (competing flow) | 266 Mbit/s | 559 Mbit/s | 2.10× |
| wan50 | lat64 p50 | 102 ms | 101 ms | 0.99× |
| wan50 | lat64 p99 | 119 ms | 119 ms | 1.00× |
| wan50 | lat64load p50 | 147 ms | 113 ms | **0.77×** |
| wan50 | lat64load p99 | 1,237 ms | 703 ms | **0.57×** |
| wan50 | comp | 91.7 Mbit/s | 154 Mbit/s | 1.68× |
| lossy2 | lat64 p50 | 162 ms | 162 ms | 1.00× |
| lossy2 | lat64 p99 | 368 ms | 362 ms | 0.98× |
| lossy2 | lat64load p90 | 523 ms | 366 ms | **0.70×** |
| lossy2 | lat64load p99 | 900 ms | 774 ms | 0.86× |
| lossy2 | comp | 76.1 Mbit/s | 119 Mbit/s | 1.56× |

**Idle, the two are indistinguishable.** At 100 ms and 160 ms RTT every percentile matches to
within 2 %, which is the right answer: the path dominates and neither implementation adds
anything to it. Only on `clean`, where there is no path to dominate and the numbers are a few
hundred microseconds, does the difference in per-packet cost show as latency.

**Under load Rust is ahead on both axes at once**, which is the part worth stating carefully: its
p99 is 0.31–0.86× Go's *while its competing flow carried 1.6–2.1× as much data*. The comparison
is therefore not rate-matched — Rust's probe is queueing behind more traffic, not less — so the
latency advantage is the conservative reading of these rows, not the flattering one. On `clean`,
one row goes the other way for the same reason (`lat64load` p90 0.35 ms for GG against 3.99 ms
for RR, while RR moved 2.1× the bytes); the tail, where queueing actually hurts, is 0.31×.

No error and no lost connection in any latency run, on any pair, on any profile.

    --profiles "clean lan wan50 lossy2 lossy10 burst ratelimited"

# 11.4: the six-hour soak, and the D07 allocator comparison

Two separate questions were answered with the same scenario (`tools/lab/scenarios/soak-s1-wan50.json`:
S1 config, `wan50` netem, 20 streams/s of 10 kB–1 MB churn, 10 long-lived streams, an 8 MB × 4 burst
every five minutes, a 64-byte latency probe alongside, sampled every 60 s).

1. **Does the port pass 11.4?**: a side-by-side Go/Rust pair on two near-identical 1-vCPU x86_64
   boxes, same six hours, same wall clock.
2. **Which libc do the Linux release artifacts use (DECISIONS D07)?**: the same scenario run twice
   on *one* host, changing nothing but the allocator.

Acceptance for (1) is **step 11.4's**: RSS and fd count flat after warm-up, no monotonic growth,
no errors. Not the endpoint values: the slopes. `lab.py` computes them as least-squares gradients
over every sample past the warm-up cutoff (the later of ten minutes and a tenth of the run; 2160 s
for a six-hour run), because `first→last` cannot tell a one-off step from a leak.

### The acceptance numbers: slopes after warm-up

| | Rust client | Rust server | Go client | Go server |
|---|---:|---:|---:|---:|
| **RSS slope** | **+537 kB/h** | **+201 kB/h** | +973 kB/h | +567 kB/h |
| **fd slope** | **−0.0 /h** | **+0.0 /h** | +0.4 /h | +0.5 /h |
| RSS first→last | 4.3 → 42.1 MiB | 5.1 → 47.6 MiB | 15.6 → 222.8 MiB | 15.2 → 235.8 MiB |
| RSS max | 43.5 MiB | 49.6 MiB | 222.8 MiB | 261.7 MiB |
| VmHWM | 45.5 MiB | 49.6 MiB | 222.8 MiB | 261.9 MiB |
| fds first→last | 10 → 1231 | 10 → 1225 | 6 → 1179 | 6 → 1172 |
| CPU (6 h) | 1476 s | 1487 s | 6822 s | 6843 s |

**Both sides pass, and both slopes are plateau drift rather than growth.** +537 kB/h over six hours
is +3.2 MiB on a process that sits between 39 and 43 MiB the whole time: the half-hourly samples go
40.9, 39.9, 39.2, 40.4, 40.6, 40.7, 41.8, 42.2, 42.8, 41.5, 41.4, 42.1 MiB, which is a band, not a
ramp. Go's +973 kB/h is the same kind of drift on a ~185 MiB plateau that its GC oscillates around.
The fd slopes are the flat ones that matter: the descriptor count sits at 1230 ± 5 for six hours
under a 30 s `closewait` linger at 20 streams/s (D28), so the linger reaches a steady state and does
not accumulate.

The two boxes are near-identical but not identical (different Ubuntu releases), **and the Go box was
CPU-saturated while the Rust box was not**: 6822 s of client CPU against 1476 s on a single core,
load 2.16 against 0.25. The two delivered the same offered load (the churn is rate-driven, not
capacity-driven, so both landed on ~36.8 Mbit/s), so the latency gap is what that saturation costs
rather than a protocol difference. Treat the RSS and fd slopes as the comparable numbers and the
percentiles as indicative.

### The 11.1b watch item, answered

12.3b's `memory::trim_when_idle` is process-wide and all-or-nothing: it fires only when the whole
process has moved less than 64 kB for a full 30 s tick. **Under this soak's continuous churn it never
fires at all**, by construction, the churn moves ~37 Mbit/s every tick for six hours. So the flat
Rust plateau above was held **without** the trim ever running. That is a finding about the trim's
design (it is dead weight while a process is busy, exactly as `crates/kcp/src/memory.rs` warns) and
*not* a soak failure: on glibc, ordinary `free` gives the pages back without being asked. Section 2
is what happens when the allocator does not.

## 2. D07: the controlled allocator comparison

D07 had flip-flopped twice, and the evidence that remained was **confounded**. The same scenario had
produced 253 MiB of client RSS on lab-arm64 (aarch64, 2 vCPU, **static musl**) and 42 MiB on
lab-x86-2 (x86_64, 1 vCPU, **glibc**): a 6× gap that looked like the allocator but could equally
have been the architecture, the core count or the load.

So the scenario was run a **third** time, on **lab-arm64**, with the **glibc** build. Same host, same
architecture, same netem profile, same S1 flags, same churn seed, same workload driver binary (the
`kr-pingpong`/`kr-labsample` pair was *not* re-deployed, so the load generator is byte-identical to
the musl run's). **Only `kr-client` and `kr-server` changed**, from
`aarch64-unknown-linux-musl` to `aarch64-unknown-linux-gnu` targeting glibc 2.17
(`tools/lab/deploy.sh --arch aarch64 --gnu --rust`).

**Two hours, not six**, and the existing curves are why. The musl client passed 62 MiB at 15 minutes
and 135 MiB at two hours, climbing ~42 MiB/h through that window: already **3× the entire six-hour
glibc plateau on lab-x86-2**, while both glibc runs were inside their final band before the first
hour was out. A ratchet of that size cannot hide for two hours, and the release measurement that
settles the second half of the question happens in the 120 seconds after the traffic stops. Six
hours would have re-measured a decided question on the production host for four extra hours.

### The confounds this removes, and the ones left

Removed outright, because one box held them constant: **architecture** (both aarch64 Neoverse-N1),
**core count** (both 2 vCPU), **kernel and distribution** (the same Ubuntu 24.04 install), **netem
profile**, **flags**, **churn seed**, and **the workload driver binary**.

The "lower throughput means less allocation churn" worry turns out not to have applied in the first
place: the churn workload is **rate-driven, not capacity-driven**, so every run of this scenario
lands on the same offered load. All four runs measured 36.7–36.8 Mbit/s, and the two lab-arm64 runs
agree to three digits on latency as well (p50 103.02 ms both, p90 115.61 / 116.13 ms, p99 190.32 /
192.41 ms). Client CPU was **8.5 % of one core in both** (610 s over 2 h; 1833 s over 6 h), and the
background production mesh sat at mean load 0.50 during the glibc run against 0.51 during the musl
one. The two processes did the same work at the same rate on the same machine.

What is **not** controlled:

1. **One run per build.** No repetitions, no interleaving: step 12 rule 1 is not met. The effect is
   5× in peak and 75× in slope, which is orders of magnitude outside any plausible run-to-run
   spread, but it is still n=1 per arm.
2. **Different durations** (2 h against 6 h). The table's peak column therefore compares musl's
   six-hour peak with glibc's two-hour peak. Restricting musl to the same two hours only moves it
   from 253.0 to 135.2 MiB, still 2.7× glibc's peak and still climbing at 45 MiB/h at the cut.
3. **Different wall clock.** The musl run was 16:28–22:28Z, the glibc run 02:08–04:08Z, so the
   neighbours on the production box were not literally the same traffic. The load averages match to
   0.01 and neither run was near saturation.
4. **The binaries differ in more than libc.** A gnu target is a PIE against the system libc; the
   musl one is a static executable. Nothing else in the build changed (same revision, same
   `release` profile, same features, no `#[global_allocator]` in either).

### What D07 should say

**Keep glibc as the default for the Linux release artifacts, and keep static musl only as a
documented portable fallback that keeps its high-water mark.** That is what D07 already says after
12.3b, and the soak does not overturn it: it removes the last reason to doubt it. 12.3b measured
95.6 % released against 4.9 % with `memprobe`, a single-purpose probe on a synthetic burst; this is
the real `kr-client`/`kr-server` pair, under six and two hours of production-shaped churn, on one
machine, with a 253 MiB versus 50 MiB outcome and 73 % versus 0 % returned.

It also closes 12.3b's caveat 13 (the fix was only ever measured on a single-workload process that
goes fully quiet) and answers memory.md follow-up 1's "still open underneath it": the real two-process
pair under load does release, and it releases on the first quiet tick.

The one genuinely new thing the soak adds is the shape of the musl failure. `memprobe` measured musl
**not giving a burst back**; the soak shows that under sustained churn it never gives *anything*
back, so the high-water mark is not a high-water mark at all but a **monotone ramp of ~32–45 MiB per
hour with no ceiling in six hours**. On a 961 MB box like lab-x86-3 that is an OOM in a day. If a
musl artifact continues to ship, that sentence belongs next to it, and it is a stronger warning than
"keeps its high-water mark".
